# ADR 0007: Self-Hosted Scheduling (`/book`)

- Status: Accepted
- Date: 2026-06-14

## Context

The portfolio needs a way for visitors to book a call without depending on the
Calendly SaaS. This introduces the first stateful backend in an otherwise
static-content site: persisted bookings, outbound email, and (Phase 2) two-way
Google Calendar sync. The design spec lives at
`docs/superpowers/specs/2026-06-14-self-hosted-scheduling-design.md`; the
phased plan at `docs/superpowers/plans/2026-06-14-scheduling-phase1.md`.

These choices add long-term dependencies, so they are recorded here per the
project's dependency-ADR rule.

## Decision

- **Persistence: Neon Postgres** via `@neondatabase/serverless` (HTTP driver,
  low cold-start on Vercel Functions). Bookings are the source of truth, with a
  Postgres `EXCLUDE USING gist` constraint making overlapping confirmed
  bookings impossible at the database level. Chosen over Vercel KV/Upstash
  because relational integrity + the exclusion constraint give correctness for
  free; chosen over an ORM (Drizzle/Prisma) to avoid a heavier dependency for a
  single small table — raw parameterized SQL in `src/lib/scheduling/bookings.ts`.

- **Email: Resend** (`resend`) for confirmation + owner-notification emails with
  an attached `.ics`. Generous free tier, first-class on Vercel. The `.ics` is
  generated by a tiny hand-rolled builder (`src/lib/scheduling/ics.ts`) rather
  than adding an `ics` package.

- **Dates: `date-fns` + `date-fns-tz`** (tree-shakeable) for timezone-correct
  slot math in the pure availability engine and client-side rendering. Chosen
  over Luxon (heavier) and the Temporal polyfill (still maturing).

- **Config in code, not an admin UI.** Meeting types and weekly availability
  live in `src/content/scheduling.ts`, matching the existing content convention.

- **Google sync via service account (Phase 2), not interactive OAuth.** The
  owner shares their calendar with a service account; the app authenticates with
  a static key. Avoids OAuth's 7-day refresh-token expiry in testing mode and
  needs no callback route. (Recorded now; implemented in Phase 2.)

## Consequences

Positive:

- Fully self-owned scheduling — no third-party booking SaaS.
- Database-enforced correctness against double-booking.
- Server-only integrations (Neon/Resend/Google) keep the client bundle lean;
  only `date-fns`/`date-fns-tz` ship to the browser.

Tradeoffs:

- First stateful backend means new operational surface: a database, an email
  provider, and required env vars (`DATABASE_URL`, `RESEND_API_KEY`,
  `OWNER_EMAIL`, `OWNER_TIMEZONE`).
- `db/schema.sql` must be applied manually to Neon before first use (no
  migration tooling yet — acceptable for one table).
- Resend's `from` domain (`jossue.dev`) must be verified before email delivery
  works in production.
